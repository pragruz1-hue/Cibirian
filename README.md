# Cibirian — интернет-магазин профессиональной косметики

Приложение-витрина, повторяющее структуру и механику сайта
[sibcirulnik.ru](https://sibcirulnik.ru) («Сибирский цирюльник»): каталог, карточки товаров,
цены, фильтры, корзина, избранное, кабинет и информационные разделы.

Стек: **Next.js 15 (App Router) + React 19 + TypeScript**, без UI-библиотек — вся вёрстка
и дизайн-система написаны вручную.

---

## Запуск

```bash
npm install
npm run dev        # http://localhost:3000
```

Продакшен-сборка:

```bash
npm run build
npm start
```

Проверки:

```bash
npm run typecheck  # tsc --noEmit
```

Сервер биндится на `0.0.0.0`, поэтому работает в контейнерных preview-средах.

## Что реализовано

### Каталог и карточки товаров
- Полное дерево разделов: 8 корневых категорий и вложенные подразделы
  (уход за волосами → 11 типов средств, лицо → 10, тело → 5, руки и ноги → 3 и т. д.).
- URL идентичны оригиналу: `/catalog/<раздел>/<подраздел>/<slug-товара>`.
  Обслуживаются одним catch-all маршрутом `src/app/catalog/[...slug]/page.tsx`,
  который различает раздел и карточку товара.
- Карточка товара: бейджи **Хит / Советуем / Акция / Новинка / Под заказ**, бренд, линейка,
  рейтинг со звёздами, цена (в т. ч. зачёркнутая старая и процент скидки),
  наличие, кнопка «В корзину» / «Заказать», избранное, «Быстрый просмотр».
- Страница товара: галерея с миниатюрами, характеристики, вкладки
  «Описание / Характеристики / Применение / Доставка и оплата», блок «С этим товаром покупают»,
  микроразметка Schema.org `Product` + `Offer`.
- 158 статических страниц генерируются через `generateStaticParams` (SSG).

### Фильтры и сортировка
- Фасеты: бренд, назначение, тип волос, объём, диапазон цен (поля + слайдер).
- Отметки: Хит, Акция, Советуем, Новинки, «Только в наличии» — со счётчиками.
- 8 вариантов сортировки — те же, что на оригинале: популярные, по алфавиту (А→Я и Я→А),
  непопулярные, дешёвые, дорогие, по возрастанию и убыванию наличия.
- Применённые фильтры показываются тегами и снимаются по одному.
- Два режима вывода: плиткой и списком. Пагинация по 12 товаров.

### Покупательский функционал
- Корзина: drawer + отдельная страница с оформлением заказа в 4 шага
  (состав → получатель → доставка → оплата), валидацией полей, прогрессом
  до бесплатной доставки и экраном подтверждения с номером заказа.
- Избранное, история просмотров, личный кабинет.
- Состояние хранится в `localStorage` через `ShopProvider` (Context API),
  переживает перезагрузку страницы.
- Живой поиск с подсказками в шапке + страница результатов.
- Выбор города (20 городов), формы «Заказать звонок» и обратной связи,
  чат-виджет поддержки, всплывающие уведомления.
- Полная адаптивность: мега-меню, выдвижное мобильное меню, нижняя панель навигации.

### Информационные разделы
`/sales`, `/brands`, `/services`, `/contacts`, `/company`, `/company/reviews`
(с формой добавления отзыва и рейтингом), `/company/licenses`, `/company/docs`,
`/info/requisites`, `/blog`, `/landings`, `/personal`, `not-found`.

### SEO
- `generateMetadata` для каждого раздела и товара (title, description, Open Graph).
- `sitemap.ts` (все разделы и товары) и `robots.ts`.
- Семантическая вёрстка, `aria`-атрибуты, поддержка `prefers-reduced-motion`.

## Данные

Каталог собирается из трёх JSON-файлов в `src/data/`:

| Файл | Содержимое |
| --- | --- |
| `categories.json` | дерево разделов с оригинальными slug, названиями и иконками |
| `products.json` | товары витрины: название, бренд, линейка, раздел, цена, объём, наличие, отметки, фото, артикул и дословное описание с сайта |
| `site.json` | телефоны, города, бренды, навигация, варианты сортировки, виджет |

`products.json` — это узкая схема витрины (`Product` из `src/lib/types.ts`). Все
остальные данные карточки — свойства со страницы, SEO-поля, рейтинг, текстовые версии
описаний, сырая нода JSON-LD — уходят в `export/products.jsonl` для бэкенда и в витрину
не попадают: `toAppSchema` в парсере работает как явный белый список.

**В выборке 78 реальных SKU** — названия, бренды, линейки, цены, объёмы, отметки
и ссылки на фото взяты из публичного каталога исходного сайта.

Покрыты бренды: OLLIN, TEFIA, EXITO, KAARAL, KEBREN, CONCEPT, NEXXT, KONDOR,
ARAVIA PROFESSIONAL, DOMIX, RUNAIL. Разделы с товарами: шампуни, бальзамы и
кондиционеры, маски, масла, спреи, стайлинг, окрашивание, косметика для тела,
для рук и ног, для лица, подарочные наборы.

Два ограничения, о которых нужно знать:

1. **Объём.** Полный каталог сайта — несколько тысяч позиций (только в «Средствах для ухода
   за волосами» 644 товара). Песочница, в которой собиралось приложение, не имеет прямого
   сетевого доступа к сайту, данные читались постранично, поэтому в сборку вошла
   репрезентативная выборка, а не всё. Механика при этом полностью рабочая: фильтры,
   сортировка и пагинация рассчитываются из данных и корректно отработают на полном каталоге.
   **Добрать остальное можно у себя на машине** — для этого в репозитории есть парсер
   `scripts/scrape-catalog.mjs` (см. ниже).

2. **Описания и фото.** Описание карточки берётся **дословно с сайта-оригинала** и хранится
   в поле `descriptionHtml` (способ применения — в `applicationHtml`, артикул продавца —
   в `sku`). Формулировки, порядок блоков и авторская орфография сохраняются как есть:
   клиент сверяет карточку с сайтом, и любое расхождение его запутает. Пока дословное
   описание есть не у всех позиций — для остальных остаётся генератор по характеристикам
   (`src/lib/describe.ts`) с плашкой о том, что текст составлен по характеристикам; когда
   описание с сайта добавлено, плашка и сгенерированный текст автоматически скрываются.
   Фотографии подключены хотлинком с CDN `sibcirulnik.ru`; если CDN запретит хотлинк,
   компонент `Img` покажет аккуратный плейсхолдер с инициалами бренда.

   Дословный текст приходит вместе с чужой разметкой, поэтому перед выводом проходит
   `src/lib/sanitize.ts`: белый список тегов, все атрибуты снимаются, `script`/`iframe`/`svg`
   удаляются вместе с содержимым, ссылки разворачиваются в текст, а `<img>` остаётся только
   с домена-оригинала и только из `/upload/`. Формулировки это не затрагивает — теряются
   лишь классы и обработчики событий.

### Как залить полный каталог

В репозитории есть готовый импортёр — `scripts/import-bitrix.mjs`. Он принимает штатную
выгрузку каталога 1С-Битрикс и приводит её к схеме приложения.

```bash
# посмотреть, что получится, без записи файлов
npm run import:dry -- export/catalog.xml

# импортировать (заменит src/data/products.json)
npm run import -- export/catalog.xml

# долить к существующим товарам, а не заменять
npm run import -- export/catalog.xml --merge

# prайс в CSV с заголовком
npm run import -- price.csv
```

**Поддерживаемые форматы**

1. **XML «Коммерческая информация»** (ВерсияСхемы 2.02–2.05+) — экспорт из
   «Магазин → Настройки → Экспорт данных». Читаются все три секции:
   `Классификатор` (дерево групп), `Каталог` (товары и свойства),
   `ПакетПредложений` (цены и остатки).
2. **CSV с заголовком** — разделитель `,` или `;` определяется автоматически,
   кавычки и многострочные поля поддерживаются.

**Что делает импортёр**

- строит путь раздела из иерархии групп (`Код` группы, иначе транслитерация названия);
- берёт цену из `ПакетПредложений`, старую цену — из типа цены с `OLD`/`старая` в коде;
- наличие — из `Количество` (`> 0` → в наличии);
- бренд — из свойства, иначе определяет по названию (17 известных марок + запасное правило);
- нормализует объём к одному формату: `1000` → `1000 мл`, `1 000 мл` → `1000 мл`,
  `500 g` → `500 г`; наборы вроде `2×100 мл` не схлопывает;
  единый формат важен — иначе фасет объёма в фильтре раздваивается;
- подхватывает несколько фото (`Картинка`) и relative-пути `upload/...`,
  достраивая их до абсолютных;
- читает отметки Хит / Советуем / Акция / Новинка из свойств;
- отбрасывает товары с `CML2_ACTIVE = false` и дубликаты по `раздел + slug`;
- транслитерирует slug по правилам Битрикса, если поле `Код` пустое;
- выгружает дерево разделов отдельно в `categories.imported.json`.

**Полезные опции**

| Опция | Зачем |
| --- | --- |
| `--brand-prop BRAND` | код свойства с брендом, если он нестандартный |
| `--volume-prop OBYOM` | код свойства с объёмом |
| `--price-type BASE` | брать только конкретный тип цены |
| `--merge` | не заменять `products.json`, а долить новые позиции |
| `--dry-run` | отчёт и примеры записей без записи на диск |
| `--out <каталог>` | писать в другой каталог (удобно проверить, не трогая боевые данные) |

После импорта компоненты править не нужно: фасеты фильтров, счётчики разделов,
сортировка и пагинация пересчитываются из данных автоматически. Достаточно
`npm run build && npm start`.

XML-парсер в импортёре написан вручную и не тянет зависимостей — скрипт запускается
голой `node` без установки пакетов.

### Как спарсить каталог прямо с сайта

Если выгрузки из Битрикса под рукой нет, каталог собирается с публичных страниц —
`scripts/scrape-catalog.mjs`. Зависимостей тоже нет, нужен Node 18+ (встроенный `fetch`).
Запускать нужно **у себя на машине**: песочница, где собиралось приложение, до сайта
не достаёт.

```bash
# 1. Разведка: найти все URL, показать статистику и оценку времени, ничего не качая
npm run scrape:dry

# 2. Пробный прогон на 20 карточках; сырой HTML складывается в .scrape-cache/html
npm run scrape:try

# 3. Полный прогон: заменит src/data/products.json, допишет новые разделы
#    в src/data/categories.json и соберёт выгрузку для бэкенда в export/
#    (прежние версии — в .scrape-cache/products.backup.json и categories.backup.json)
npm run scrape

# 4. Продолжить после обрыва связи — прогресс в .scrape-cache/progress.json,
#    уже собранные карточки в .scrape-cache/records.jsonl
npm run scrape:resume
```

**Почему через sitemap, а не по страницам листинга.** В `robots.txt` сайта пагинация
закрыта явно — `Disallow: *PAGEN_*=`, — зато указан адрес `Sitemap:`. Обход по sitemap
даёт полный список карточек без единого запроса к закрытым адресам, поэтому он
и вежливее, и надёжнее: не зависит от того, на сколько страниц раздел разбит
и в каком порядке товары на них стоят. Скрипт читает `robots.txt`, раскрывает индекс
sitemap'ов рекурсивно и затем дополнительно проверяет каждый URL по Disallow-правилам
(битриксовые `*` и `$` понимаются, побеждает самое длинное совпадение).

**Как разделы отличаются от товаров.** Раздел — это URL, который является префиксом
другого URL; карточки всегда листья. Проверка делается по самому списку и не требует
ни одного дополнительного запроса к сайту.

**Разбор карточки идёт в четыре уровня надёжности**, и уровни между собой не смешиваются:

1. JSON-LD `@type: Product` → `offers.price`;
2. микроразметка `itemprop="price"` и `meta property="product:price:amount"`;
3. текст внутри блоков, у которых в `class` есть `price`;
4. только если первые три уровня пусты — все «N руб» на странице с проверкой контекста.

Смешивать уровни нельзя: цена похожего товара из блока «Рекомендуем» (120 руб)
перевесила бы настоящую (850 руб), если брать минимум по всем находкам. Отдельно
отсекаются служебные зоны — доставка («бесплатно от 3 000 руб»), подвал, блоки
похожих и просмотренных товаров. Старая цена ищется в блоках `price_old`/`discount`,
поэтому скидка не теряется, когда в JSON-LD указана только текущая цена. Скрытый
артефакт вёрстки «1320 rub.» игнорируется: ищутся только `руб` и `₽`.

**Что ещё извлекается:** бренд и линейка, объём, наличие и его текстовая формулировка,
отметки Хит / Советуем / Акция / Новинка, предзаказ, артикул и внешний id, назначение,
тип волос, палитра, хлебные крошки, рейтинг и число отзывов, SEO-поля страницы
(`meta title`, `meta description`, `canonical`, `og:title`, `h1`) и фото.
Превью из `resize_cache` разворачиваются в оригиналы — иначе в каталоге будут
мыльные картинки 300×300. По хлебным крошкам автоматически строится
`categories.scraped.json` с человекочитаемыми названиями разделов: слаг
`professionalnaya_kosmetika_dlya_volos` получает имя «Профессиональная косметика для волос».

Все пары «свойство → значение» из таблицы характеристик снимаются целиком и в исходном
регистре названий — это источник правды для бэкенда, а `purpose`/`hairType`/`palette`
лишь производные от них поля для фильтров витрины. Плюс в запись кладётся сырая нода
JSON-LD: если сайт отдаёт поле, о котором парсер не знает, оно всё равно доедет
до базы и его не придётся собирать повторным обходом.

Страница, на которой не нашлось пары «название + цена», товаром не считается — так
из результата выпадают попавшие в sitemap страницы офисов продаж
(`/catalog/ofis_prodazh_karbolitovskaya_16_a/`). Страница раздела, где цен десятки,
а разметки товара нет, отбрасывается тем же правилом.

**Описания берутся с сайта дословно** — вместе со структурой: абзацы, списки
«АКТИВНЫЕ КОМПОНЕНТЫ», буллеты с «·», блок «Способ применения». Клиент сверяет
карточку с оригиналом, поэтому пересказ недопустим; опечатки сайта тоже сохраняются
как есть. `src/lib/describe.ts` работает только запасным вариантом — для карточки,
где текста на сайте нет вовсе. Перед выводом HTML проходит `src/lib/sanitize.ts`
(срезаются скрипты, обработчики событий, комментарии, чужие домены в ссылках).

**Полнота охвата.** Основной источник — sitemap, но полагаться только на него нельзя:
Битрикс пересоздаёт его по расписанию, и свежая карточка могла туда ещё не попасть.
Поэтому в полном прогоне парсер дополнительно обходит страницы разделов и добирает
карточки, которых в sitemap нет (`--discover-listings`). Пагинацию при этом не трогаем —
`*PAGEN_*=` закрыт в `robots.txt`, так что берётся только первая страница каждого
раздела: обход остаётся в рамках разрешённого, а всё, что лежит глубже, приходит
из sitemap. В отчёте видно, сколько карточек нашлось сверх sitemap; если ноль —
расхождений нет и охват полный.

**Вежливость и надёжность.** По умолчанию пауза 400 мс между запросами и 2 параллельных
потока — на нескольких тысячах карточек это примерно 25–40 минут. Состояние прогона
разнесено на два файла: `.scrape-cache/progress.json` хранит только карту готовности
и перезаписывается каждые 25 товаров, а сами записи пишутся append-only в
`.scrape-cache/records.jsonl` — по строке на карточку. Раньше товары лежали внутри
`progress.json`, и каждый checkpoint перезаписывал весь массив: на тысячах SKU
с описаниями это десятки мегабайт на запись, то есть гигабайты диска к концу прогона.
Теперь обрыв связи не теряет уже собранное, а `--resume` продолжает с места обрыва;
если обрыв пришёлся на середину строки, товар помечается для повторного запроса,
а не теряется молча. Ошибки пишутся в `.scrape-cache/errors.log`.

| Опция | Зачем |
| --- | --- |
| `--dry-run` | разведка без единого запроса к карточкам |
| `--limit 20` | пробный прогон на первых 20 товарах |
| `--save-html` | складывать сырой HTML в `.scrape-cache/html` |
| `--html page.html <url>` | разобрать сохранённую страницу и показать, что извлечено |
| `--urls-only файл` | выгрузить найденные URL и выйти |
| `--delay 800 --concurrency 1` | ещё осторожнее к сайту |
| `--only подстрока` / `--skip подстрока` | сузить набор URL, например до одного раздела |
| `--sitemap <url>` | задать sitemap явно, минуя `robots.txt` |
| `--out <каталог>` | писать не в `src/data`, а в другой каталог |
| `--resume` | продолжить прерванный прогон |
| `--export <каталог>` | куда писать выгрузку для бэкенда (по умолчанию `export/`) |
| `--no-export` | не писать выгрузку для бэкенда |
| `--no-discover-listings` | работать строго по sitemap, не обходя страницы разделов |
| `--no-update-categories` | не сливать разделы в `src/data/categories.json` |

### Выгрузка для бэкенда

Полный прогон (`npm run scrape`) кроме файлов витрины пишет каталог `export/` —
данные в том виде, в каком их можно загружать в базу. Витрине достаточно десяти полей,
бэкенду нужны все: свойства, состав, SEO-поля, галерея, остатки, отметки и путь раздела.
Терять их при сборе нельзя, потому что повторный обход сайта на тысячах SKU — это
ещё полчаса нагрузки на чужой сервер.

| Файл | Что это и когда брать |
| --- | --- |
| `products.jsonl` | **основной файл для импорта**: по одной JSON-записи на строку. Читается потоково, не требует загружать весь каталог в память — на тысячах SKU это десятки мегабайт |
| `products.json` | те же записи одним массивом — если загрузчик ждёт именно массив |
| `products.csv` | плоская таблица, разделитель `;` и BOM: открывается в русском Excel и грузится в 1С/CRM без настройки кодировки |
| `properties.csv` | длинная таблица `sku;sourceUrl;name;property;value`. В CSV характеристики не теряются, даже если их у товара два десятка, и не требуют отдельной колонки на каждое свойство |
| `categories.json` | разделы деревом (`tree`) и плоским списком (`flat`) с путями, глубиной, `parentPath` и счётчиком товаров — под таблицу с `parent_id` |
| `manifest.json` | что именно собрано: счётчики, список колонок, первичный ключ, размеры файлов и перечень неполных записей |

**Первичный ключ — `sourceUrl`.** Он уникален и стабилен, в отличие от `id`, который
сайт может переназначить, и от артикула, который на сайте встречается не у каждой
карточки. По нему же удобно делать повторную загрузку: `UPSERT` по `sourceUrl`
обновляет цены и остатки, не плодя дубликаты.

В записи товара: идентификация (`sourceUrl`, `sourcePath`, `slug`, `sku`, `externalId`,
`scrapedAt`), таксономия (`category`, `categoryPath`, `breadcrumbs`), основное (`name`,
`brand`, `line`, `price`, `oldPrice`, `currency`, `discountPercent`), наличие и отметки
(`inStock`, `stockText`, `availability`, `hit`, `recommend`, `sale`, `isNew`, `preorder`),
характеристики (`volume` + разложенные `volumeValue`/`volumeUnit`, `purpose`, `hairType`,
`palette` и полный словарь `properties`), контент (`descriptionHtml`/`descriptionText`,
`applicationHtml`/`applicationText`, `metaTitle`, `metaDescription`, `canonical`,
`pageTitle`, `h1`), медиа (`images`, `mainImage`), отзывы (`rating`, `reviewsCount`)
и сырая нода `jsonLd`.

Загрузка в PostgreSQL — три шага: целевая таблица, staging для строк JSONL и `UPSERT`.

```sql
CREATE TABLE products (
  source_url     text PRIMARY KEY,
  sku            text,
  external_id    text,
  name           text NOT NULL,
  brand          text,
  category_path  text,
  price          numeric(10,2),
  old_price      numeric(10,2),
  currency       text DEFAULT 'RUB',
  in_stock       boolean,
  volume_value   numeric(10,3),
  volume_unit    text,
  description    text,
  application    text,
  images         text[],
  properties     jsonb,          -- весь словарь характеристик как есть
  raw            jsonb,          -- полная запись: при импорте ничего не теряется
  scraped_at     timestamptz
);

-- Строка JSONL = строка таблицы. \copy читает файл на стороне клиента,
-- поэтому права суперпользователя и server-side COPY не нужны.
CREATE TEMP TABLE staging (line text);
\copy staging(line) FROM 'export/products.jsonl'

INSERT INTO products
SELECT
  r->>'sourceUrl',
  r->>'sku',
  r->>'externalId',
  r->>'name',
  r->>'brand',
  r->>'category',
  NULLIF(r->>'price', '')::numeric,
  NULLIF(r->>'oldPrice', '')::numeric,
  COALESCE(r->>'currency', 'RUB'),
  COALESCE((r->>'inStock')::boolean, false),
  NULLIF(r->>'volumeValue', '')::numeric,
  r->>'volumeUnit',
  r->>'descriptionText',
  r->>'applicationText',
  ARRAY(SELECT jsonb_array_elements_text(r->'images')),
  COALESCE(r->'properties', '{}'::jsonb),
  r,
  NULLIF(r->>'scrapedAt', '')::timestamptz
FROM (SELECT line::jsonb AS r FROM staging WHERE line <> '') s
ON CONFLICT (source_url) DO UPDATE SET
  price        = EXCLUDED.price,
  old_price    = EXCLUDED.old_price,
  in_stock     = EXCLUDED.in_stock,
  description  = EXCLUDED.description,
  images       = EXCLUDED.images,
  properties   = EXCLUDED.properties,
  raw          = EXCLUDED.raw,
  scraped_at   = EXCLUDED.scrapedAt;
```

Повторная загрузка свежего прогона по `sourceUrl` обновляет цены, остатки и описания,
не плодя дубликаты. Если схема базы ещё не устоялась, можно не раскладывать поля
вовсе: залить JSONL в одну `jsonb`-колонку и выбирать нужное запросами — тогда импорт
не зависит от набора колонок и ни одно поле не потеряется.

Свойства удобно хранить отдельной таблицей — ровно её и даёт `properties.csv`:

```sql
CREATE TABLE product_properties (
  source_url text REFERENCES products(source_url) ON DELETE CASCADE,
  property   text,
  value      text,
  PRIMARY KEY (source_url, property)
);
\copy product_properties FROM 'export/properties.csv' DELIMITER ';' CSV HEADER
```

`products.csv` грузится тем же `\copy ... DELIMITER ';' CSV HEADER`: BOM в начале файла
PostgreSQL понимает, русский Excel — тоже.

Перед загрузкой стоит открыть `manifest.json`: `stats` покажет, сколько записей
с описанием, с фото, в наличии и со скидкой, а `incomplete` перечислит карточки,
где не хватает имени, цены, фото, описания, артикула или раздела. На полном каталоге
таких единицы — обычно это карточки, которые сайт отдаёт без цены (сняты с продажи),
и решать, заводить ли их в базу, лучше осознанно, а не постфактум.

Каталог `export/` добавлен в `.gitignore`: это генерируемые данные на десятки
мегабайт, в репозитории им делать нечего.

### Разделы и `categories.json`

Страницы разделов генерируются по `src/data/categories.json` (`generateStaticParams`
в `src/app/catalog/[...slug]/page.tsx`), поэтому новый раздел, которого нет в этом
файле, дал бы 404, даже если товары в нём собраны. Полный прогон сливает найденные
разделы в `categories.json` автоматически; частичный (`--limit`, `--only`) — не трогает.

Слияние — строго объединение, ничего не теряющее. Просто перезаписать файл нельзя
по двум причинам: дерево парсера строится только по товарам, так что раздел без
товаров в него не попадает, а в `categories.json` живут иконки, `shortName`, `title`
и `count` («N товаров на сайте»), которых парсер не знает. Поэтому существующие узлы
сохраняются вместе со своими полями и в своём порядке, а новые разделы добавляются
в конец своего уровня. Прежняя версия файла копируется в
`.scrape-cache/categories.backup.json`.

### Если сайт поменял вёрстку, править нужно селекторы в `extractPrices`, `extractImages`
и `extractBadges`. Чтобы не ломать уже работающее, есть тесты — `npm run test:parser`.
Они не требуют сети и проверяют парсер на фикстурах, повторяющих реальную разметку
Битрикс/Аспро: полная карточка с JSON-LD, стикерами, галереей и блоком похожих товаров;
карточка без JSON-LD на одном `itemprop`; страница офиса; страница раздела; настоящий
`robots.txt` сайта и настоящие пути из его sitemap. Отдельно проверяется, что выход
парсера совпадает со схемой `Product` из `src/lib/types.ts`, — иначе `products.json`
не соберётся в билде.

```bash
npm run test:parser
# ═══════ ИТОГ: 156 пройдено, 0 провалено ═══════
```

Порядок подстройки такой: `npm run scrape:try` → берёте из `.scrape-cache/html` страницу,
которая разобралась плохо → `npm run scrape -- --html .scrape-cache/html/<файл>.html <url>`
и смотрите, какое поле потерялось → правите селектор → `npm run test:parser` → повторяете
пробный прогон.

**Перед реальным прогоном стоит запустить сквозной тест** — `npm run test:scrape`.
Он поднимает локальную копию структуры сайта (`scripts/fixture-site.mjs`: robots.txt,
индекс sitemap, sitemap каталога, карточки в разметке Битрикс/Аспро, страницы офисов
и страница раздела) и прогоняет против неё настоящий парсер — с сетью, очередью
запросов и записью файлов. Проверяется то, что `test:parser` покрыть не может:

- весь путь от `robots.txt` до `products.json` и `categories.scraped.json`;
- что мусорные листья из sitemap не стали товарами и попали в `errors.log`;
- цены, скидки, наличие, отметки, артикулы, фото и описания в готовом файле;
- что выход соответствует схеме `Product` и что `id` идут подряд с единицы;
- **детерминизм**: второй прогон обязан дать побайтово тот же файл. Запросы идут
  параллельно, поэтому без явной сортировки `id` зависели бы от тайминга сети и
  перемешивались при каждом запуске — а к `id` привязаны рейтинг, счётчик
  просмотров и корзина в `localStorage` покупателя;
- что `--limit` и `--resume` вместе дают полный каталог без дубликатов;
- что закрытые `robots.txt` адреса и пагинация не запрашивались;
- **пригодность выгрузки для бэкенда**: все шесть файлов на месте, JSONL разбирается
  построчно и заканчивается переносом, первичный ключ `sourceUrl` уникален и абсолютен,
  у каждой записи есть имя, цена, валюта, раздел, описание, фото и свойства, CSV начинается
  с BOM и разделён `;` и CRLF, `properties.csv` — длинная таблица, счётчики и размеры
  файлов в `manifest.json` совпадают с фактическими, выгрузка воспроизводима побайтово
  (кроме даты сбора), а после `--resume` в ней столько же записей и нет дубликатов.

```bash
npm run test:scrape
# ═══════ ИТОГ: 82 пройдено, 0 провалено ═══════
```

Отдельно можно поднять фикстуру и посмотреть страницы глазами —
`npm run fixture-site` (http://127.0.0.1:3999), удобно для отладки селекторов
через `--html`.

После полного прогона достаточно `npm run build && npm start`: фасеты фильтров, счётчики
разделов, сортировка и пагинация пересчитываются из данных сами.

## Примечания по реализации

- **`next/image` не используется намеренно.** Оптимизация изображений идёт через сервер,
  а сервер в изолированной среде не может достучаться до внешнего CDN. Обычный `<img>`
  грузит фото напрямую в браузере пользователя — поэтому картинки работают.
- Юридические реквизиты (ИНН, КПП, ОГРН, банковские данные) на странице `/info/requisites`
  оставлены незаполненными: это демо-сборка интерфейса, а не данные реального юрлица.
- Отзывы в `/company/reviews` и статьи в `/blog` — демонстрационные, они показывают
  работу блоков интерфейса. Форма заказа и формы связи работают локально и никуда
  не отправляют данные.
